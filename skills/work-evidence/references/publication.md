# Public release boundary

Publish reusable instructions, templates, code and synthetic examples only. Do not copy the source user's actual timesheet, compensation, company rules, screenshots, private document URLs, repository names or conversation extracts into the package.

Before publishing, inspect the Git staged files and commit history, not merely the current README. Keep private ledgers, reports, exports, screenshots, environment files and credentials excluded. A `.gitignore` cannot remove already tracked content. Use the user's selected owner and visibility; inspect account identity and repository collisions before creating a remote. Do not overwrite an existing repository or change its visibility to finish the release.

The public documentation should say what is automated and what still depends on personal recollection or employer agreement. Do not market the skill as certifying work, guaranteeing payroll approval, or maximizing compensation. The useful promise is a traceable explanation of work with fewer omissions and arithmetic errors.

Use a standard open-source license selected or accepted by the repository owner. Document the dependency-free helper and validate it with synthetic data. If live publication lacks clear authorization or credentials, deliver a complete local package and ask the owner to approve that concrete public release.
